> ⚠️ **本文写于探测期（2026-08-26～27），部分内容已被实车结果推翻。**

> **"车机到底能不能被第三方 App 直接控制空调/座椅"**。
> 不需要 root、不需要 adb，U 盘装 APK 即可。

## 现状：壳 App 怎么用（2026-08-28）

壳已瘦身完成，车控全部在插件里。界面是顶栏 + 插件区 + 日志面板（深色，设计见 `docs/设计/壳界面/`）：车机全屏时插件区在左、日志在右；车机分屏（半屏）或手机上日志收成底部一条，点开是抽屉。

### 构建

```bash
# 壳 → app/app/build/outputs/apk/release/app-release-unsigned.apk
cd app && ./gradlew assembleRelease

# 插件 → plugin/output/plugin.dex
cd plugin && ./gradlew pluginDex
```

（命令行需先设 `JAVA_HOME`；Android Studio 内构建自带 JBR。）

### 装车与导入插件

1. 把 release APK 用车机厂商签名签好（工程里没配 signingConfig，`assembleRelease` 只产出 unsigned），U 盘装到车机。
2. 把 `plugin.dex` 也拷进 U 盘或车机存储。
3. 插件加载后先跑**启动自检**（只读，不动车）：空调、座椅两组功能的 COMMON + GET/SET 权限都已授权、AC/Setting 设备能初始化，才连接旋钮、进入车控页面。没通过时右半边固定停在「🔍 启动自检」页：列出哪项没过，按功能列出缺的权限，缺 COMMON 的那行有「🔑 申请」按钮，授权后自动重新检查，通过就直接开始连旋钮；也可以点「🔁 重新检查」。车速、车身目前只有自检在用，缺了只提示、不拦启动。车机开机没开界面时也照样检查，权限早已授过就照常连旋钮。
   车控用到的 `BYDAUTO_*_COMMON`（dangerous 级）**只在点「申请」按钮时申请**，调空调温度、调座椅时不会弹窗：没权限时这次操作什么都不做，日志记一条「没执行：缺 …，到自检页点「申请」按钮授权」。申请按钮在启动自检页（没通过时）和自检页上。点「🔧 自检」打开自检页，点「▶️ 开始自检」跑完后，页面上按功能（空调/座椅/车速/车身）列出 COMMON 和 GET/SET 的授权状态，缺 COMMON 的那行有「🔑 申请」按钮，点了才弹窗；授权后点「🔁 重新自检」看效果。GET/SET 缺了页面会注明是签名级、申请不了。GET/SET 是 signature 级，厂商签名装车即授。壳自己只管蓝牙权限：顶栏的蓝牙胶囊没授权时是红的，点它申请。
4. 点顶栏的 **「导入插件」**（没导入过插件时插件区中间也有一个），在文件选择器里选中插件包或 `plugin.dex`。壳会把它拷进 App 私有目录 `filesDir/knob/plugin.dex`、置为只读（Android 10+ 的 W^X 要求，可写的 dex 会被系统拒绝加载），然后立即加载。
5. 成功标志：插件区从"还没有导入插件"变成插件页面，顶栏插件胶囊变绿，日志出现 `✅ 插件已加载并初始化`；启动自检通过后日志出现 `✅ 启动自检通过，开始连接旋钮`，页面进入首页/空调页/座椅页。
6. 之后每次启动自动从私有目录加载，不用再选。更新插件 = 重新导入覆盖，**壳不用重装、不用重签**。

### 顶栏和日志面板

| 位置 | 作用 |
|------|------|
| 顶栏 · 插件胶囊 | 绿点 = 插件已加载（宽屏还显示导入时间），空心 = 还没导入 |
| 顶栏 · 蓝牙胶囊 | 红色带「授权」= 蓝牙权限没授，点它申请；绿点 = 已授权 |
| 顶栏 · 导入插件 | SAF 文件选择器导入插件包 / `plugin.dex`（不需要存储权限） |
| 顶栏 · 日志（宽屏）/ 底部日志条（窄屏） | 开关日志面板；收起时显示最新一条，红色角标是没看过的错误条数 |
| 日志面板 · 自动滚动 | 新日志来了滚到最新；往上翻时自动暂停，点「回到最新」恢复 |
| 日志面板 · 保存 | 导出全部日志到 `Downloads/log_<时间戳>.txt`（走 MediaStore，替代 adb logcat） |
| 日志面板 · 清空 | 清空日志 |
| 日志面板 · 全部 / 警告和错误 | 只看 ⚠️ / ❌ 的行 |

> 插件在进程启动时（`KnobApp.onCreate`）**同步**加载，界面创建时插件已就绪，冷启动即可正常渲染。
> 进程由无障碍服务在开机时拉起并保持常驻，退出界面不会断开外设连接；
> 退出时壳会发 `ui.unbind` 让插件解绑容器，再次进入自动恢复到离开时那一页。

### 车控入口在插件里

壳不再有座椅/空调按钮。车控通过 `KnobPlugin` 四功能域调用：
`onCommand("seat.ventilating", {"state":2})`、`onQuery("selfTest", {})` 等，
命令清单见 `MainPlugin.kt` 的注释与 `AGENTS.md`。

## 这是什么

一个**只读探测** App，装上后从 4 个维度检查车机暴露了什么能力：

1. **android.car.\* 接口** — 车机有没有标准的车辆控制接口（这是"直接控制"的关键）
2. **系统属性** — 只读车机硬件/平台信息
3. **已安装应用** — 列出与车控相关的包名（找到内置空调 App）
4. **无障碍** — 读取当前窗口的控件结构，看空调界面长什么样

> ⚠️ **安全声明**：本 App **只读取、不修改**任何系统设置。不会动空调、不会改温度、不会写任何东西。它只是"侦察"。

## 使用步骤（按顺序做）

> 🗄️ 这一节描述的是探测期 App 的界面（「无障碍」「全部探测」等按钮），
> 壳瘦身后这些按钮**已不存在**。保留作为当时的操作记录。
> 无障碍服务本身仍在，但现在只用于捕获蓝牙 HID 按键。

### 第 1 步：授权辅助功能
- 打开 Knob → 点「无障碍」按钮。
- 如果提示未授权，去 **系统设置 → 辅助功能/无障碍**，找到 Knob，打开开关。
- 回到 App 点「无障碍」，应显示"✅ 服务运行 / ✅ 已授权"。

### 第 2 步：全量探测
- 点「全部探测」，把结果**复制**（点「复制日志」），发给自己或留存。
- 重点看两个结论：
  - `android.car.* 接口探测` 部分是否出现 **✅ 成功 createCar()**
  - 是否出现 **❌ 无权限 / SELinux 拒绝**

### 第 3 步：关键实测 — 空调界面
这是整个验证的核心：
1. 打开车机的**空调/车控界面**（让空调界面在前台）。
2. **切回** Knob App，点「无障碍」→「转储当前窗口控件树」。
3. 看转储出来的控件树里，有没有空调温度按钮的 **resource-id**（形如 `com.xxx.aircon:id/temp_up`）。

### 第 4 步：判断结论

> 🗄️ **这一步已经做完了**，结论是「**需系统权限，第三方普通签名做不了直接控制**」。
> 下面的判断表保留作历史记录，不用再走一遍。
> 无障碍模拟点击那一行已作废 —— 该路线于 2026-08-28 弃用，项目全押官方签名。

| 探测结果 | 结论 | 实际命中 |
|---------|------|---------|
| 有 `android.car.Car` 且 `createCar()` 成功 | ✅ 可直接控制 | ❌ 未命中 |
| BYDAUTO 权限存在但 GET/SET 是 signature 级、申请被拒 | ⚠️ 需系统权限 | ✅ **命中这一条** |
| 无障碍能读到空调按钮的 resource-id | ⚠️ 可模拟点击 | 🗄️ 路线已弃用，未采纳 |
| 两者都没有 | ❌ 车控做不了 | — |

**由此确定的方向**：壳用车机厂商签名签一次 → 业务逻辑放 `plugin.dex` 热加载。
详见 `docs/壳-DEX热加载架构设计.md` 与 `docs/ROADMAP.md`。

## 常见问题

**Q：App 装不上/闪退？**
A：确认车机是 Android（非纯鸿蒙 NEXT）。若鸿蒙 NEXT，可能需要鸿蒙版本，可先确认车机底层。

**Q：无障碍开关在设置里找不到？**
A：部分车机定制系统把"辅助功能"改名为"无障碍"或"更多设置"里，仔细找；个别品牌可能隐藏，需探索。

**Q：转储控件树是空的？**
A：无障碍"读取窗口内容"权限可能被车机限制，或空调界面不允许第三方读取。这本身就是个结论。

**Q：会不会影响保修？**
A：只装普通第三方 App、不 root、不刷机，一般不影响整车保修。

## 【新增】座椅通风 + 空调温度控制 + 日志窗口

基于车机厂商官方 SDK 分析，Knob 已新增**直接车控**功能。

### ❌ 已被推翻的结论：座椅通风 / 空调「不需要提权」

> 这里原本写着「座椅通风/空调不需要提权，直接用公开 API 就能控」。
> **实车验证证明这是错的**，保留记录以免重蹈覆辙。

当时的推理是：调用链看起来完全公开 —— 先 `hasFeature("DriverSeatVentilating")` 检测车辆是否支持，
再调 `BYDAutoSettingDevice.setSeatVentilatingState(seat, level)` 下发档位，
全程没有 `setHiddenApiExemptions` 之类的提权动作，于是推断"公开 API 直接可用"。

**推理错在哪**：门槛不在 hidden API，而在 **Manifest 权限本身的 protectionLevel**。
`BYDAUTO_SETTING_GET/SET`、`BYDAUTO_AC_GET/SET` 是 **signature 级**，普通签名 App 申请也不会被授予；
能调通这些 API 的应用都持有**车机厂商签发的签名**，不是因为这些 API 公开。

**实测结果**：

- `setAcTemperature` / `setAcTemperatureControlMode` → `SecurityException: [setIntArray] permission deny!`
- `hasFeature` → `[getInt] permission deny!`，设备初始化阶段就探测不了
- `setSeatVentilatingState` → `InvocationTargetException: null`
- 读空调温度 → `-2147482645`（参数无效/不可读）

**所以本 App 的车控按钮在普通签名下全部失败**，这是预期行为，不是 bug。
车控要能跑通，唯一路线是壳用车机厂商签名（见 `docs/壳-DEX热加载架构设计.md`）。

### 🗄️ 这些车控 UI 已迁入插件

探测期壳里有「座椅通风 关闭/低档/高档」「空调区域+温度输入框」「初始化设备」「检查权限」等按钮，
**壳瘦身时全部删除**，对应能力改由插件提供：

| 原按钮 | 现在的调用 |
|--------|-----------|
| 初始化设备 | `onCommand("init.all", {})` |
| 检查权限 | `onQuery("perm.check", {})` |
| 座椅通风 关闭/低档/高档 | `onCommand("seat.ventilating", {"state": 1/2/3})` |
| 设置空调温度 | `onCommand("ac.temperature", {"area": 0~3, "value": 17~33})` |
| 读温度 / 读通风状态 | `onQuery("ac.temperature", {"area":n})` / `onQuery("seat.ventilating", {})` |
| （新增）一键全量自检 | `onQuery("selfTest", {})` |

温度范围：摄氏 17~33（`CarControl` 只走摄氏，单位常量 `AC_TEMPERATURE_UNIT_OC`）。
空调另有开关 / 风量 / 风向 / 循环 / 分控命令，清单见 `MainPlugin.kt` 注释。

日志窗口仍在壳里（车机无 adb，App 内日志是唯一观测手段），带时间戳和返回码，可清空、可导出到 Downloads。

### 返回码含义（BYDAUTO_COMMAND_RESULT）
| 返回码 | 含义 |
|--------|------|
| 0 | ✅ 成功 |
| -2147482645 | 参数无效 |
| -2147482646 | 超时 |
| -2147482647 | 忙 |
| -2147482648 | 失败 |

### 日志窗口功能
- **🧹 清空日志**：重置日志窗口
- **💾 保存日志**：导出到 `Downloads/log_<时间戳>.txt`（替代 adb logcat；日志文本本身也可长按选中复制）
