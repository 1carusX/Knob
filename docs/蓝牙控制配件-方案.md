# 目标车机 · 自定义蓝牙物理旋钮/按钮配件 — 完整 DIY 方案

> ⚠️ **已废弃**：本文档是立项初期的原始方案，第 3 节"BLE HID + 无障碍服务"这条输入路径在实测中因目标车机没有暴露无障碍设置入口而放弃，现已替换为完全自定义的双向 BLE GATT 服务。仅作历史方案保留，当前架构见 `项目历程与架构.md`。

> 适用对象：会软件开发、硬件偏弱、想边做边学的爱好者
> 车机环境：可安装第三方 App（开放安卓/鸿蒙）
> 功能目标：空调/座椅等车控 + 自定义操作
> 硬件形态：旋钮 + 若干物理按钮

---

## 0. 方案总览（一句话版）

做 **两个配套件**：
1. **硬件端**：一块内置蓝牙（HID）的单片机板 + 编码器旋钮 + 几个按键，配对后车机把它识别为"蓝牙键盘/鼠标/游戏手柄"。
2. **车机端**：一个你开发的 Android/鸿蒙 App，它一方面接收蓝牙输入并"翻译"成系统/车机动作（调空调、切模式等），另一方面（关键）负责与车机原生系统通信来真正执行车控。

核心逻辑：**硬件只管"上报按键/旋钮事件"，App 负责"解释和执行"**。这样硬件部分最简单，学习曲线最友好。


**分工原则**（这是整个项目的灵魂）：
- **硬件** = 键盘/旋钮，"不知道也不关心"自己在控制什么。
- **App** = 大脑，知道每个按键对应什么动作，并负责执行。

## 2. 硬件选型（重点：面向"硬件偏弱、边学边做"）

### 2.1 主控方案（二选一）

| 方案 | 代表板子 | 优点 | 缺点 | 适合 |
|------|---------|------|------|------|
| **A. 现成蓝牙HID模块** | ESP32-C3 / ESP32-S3 开发板 | 自带蓝牙+WiFi，Arduino生态成熟，有现成BLE HID库 | 需要自己接线、上电、做外壳 | ✅ 推荐起步 |
| **B. 成品按键/旋钮板 + 蓝牙** | 如 M5Stack、成品旋转编码器模块 | 插拔即用，几乎零焊接 | 贵、形态受限、扩展性差 | 想最快做出来 |

> **推荐方案 A（ESP32）**，理由：
> - 一颗芯片同时搞定「编码器读取 + 按键 + 蓝牙 HID」，不需要额外蓝牙模块。
> - Arduino IDE + ESP32-BLE 键盘库，代码量极小，适合学习。
> - 板子几十块人民币，坏了不心疼。

### 2.2 旋钮

- 用 **旋转编码器（Rotary Encoder）**，型号推荐 **EC11**（带按键的版本，按下也算一个按钮），几块钱一个。
- 旋钮手感：选"带定位档位"的（detented），转动时有咔哒感，车控调温时手感好。

### 2.3 按键

- 若干个 **轻触按键（tact switch）** 即可，或者买成品按键帽/按钮。
- 数量建议先 4~6 个，预留扩展口。

### 2.4 供电

- 优先 **内置锂电池**（如 18650 或 3.7V 小电池）+ 充电管理模块（TP4056，几块钱）+ 拨动开关。这样无线、不占用点烟器/USB口。

### 2.5 外壳

- 学习阶段用 **3D 打印**（网上有旋转编码器旋钮的现成模型可参考改），或者先用亚克力/热缩管+胶枪做个原型。
- 后期可用粘贴式底座固定在方向盘附近或中控合适位置。

## 3. 蓝牙连接方式（决定 App 怎么拿数据）

这是**最容易踩坑**的地方，务必先想清楚。三条路径：

### 路径 1：BLE HID（蓝牙键盘/游戏手柄）— ✅ 首选

- 硬件把自己模拟成 **蓝牙键盘**（BLE HID Keyboard）或 **游戏手柄（Gamepad/HID）**。
- **优点**：车机原生支持 HID，**无需你 App 去配对蓝牙**——系统层面就认识这个设备；按键会以系统级输入事件出现。
- **关键点**：App 不需要自己去连蓝牙，而是通过 **AccessibilityService（无障碍服务）** 或 **Input Method / key events** 捕获这些按键/旋钮事件。
- 旋钮可以映射成：左右方向键（调温）、PageUp/PageDown（切歌）等，或者映射成手柄的轴。

> 为什么是首选：系统级 HID 输入 = 你的 App 收到的是"标准按键事件"，最稳、最通用，且旋钮天然能映射成方向键/增减。

### 路径 2：自定义 BLE 数据通道（BLE GATT）

- 硬件用 BLE GATT 自定义 Service/Characteristic 上报自定义数据包。
- **优点**：数据格式完全自由（能传"事件类型+值"）。
- **缺点**：车机蓝牙连接 BLE 外设需要你 App 自己管理配对/连接（Android 上 BLE Central 由 App 发起），如果车机系统也抢着用蓝牙会有冲突；且车机断开蓝牙后 App 需重连。**复杂度高，不推荐起步。**

### 路径 3：蓝牙串口（SPP，经典蓝牙）

- 传统蓝牙串口，App 建 Socket 读数据。
- 优点：简单；缺点：Android 上 SPP 已被 Google 逐步限制（非官方 API），且车机系统可能不暴露。**不推荐。**

> **结论：用「路径 1（BLE HID 键盘/手柄）」**。App 侧通过无障碍服务读系统按键事件，稳定且绕开蓝牙配对难题。

## 4. 车机端 App 架构（你的核心代码）

### 4.1 技术栈

- **语言**：Kotlin（Android）+ 原生开发。车机是安卓/鸿蒙时，用 Android 开发最直接。
- 如果车机是鸿蒙（HarmonyOS NEXT），需评估是否兼容 Android APK；多数车机底层是 Android 定制，可装 APK。

### 4.2 App 两大模块

**模块 A：输入监听（无障碍服务）**
```kotlin
class KeyCaptureService : AccessibilityService() {
    override fun onKeyEvent(event: KeyEvent): Boolean {
        // 捕获旋钮映射的方向键/按键
        when (event.keyCode) {
            KEYCODE_DPAD_UP -> tempUp()
            KEYCODE_DPAD_DOWN -> tempDown()
            ...
        }
        return true // 消费掉，避免系统冲突
    }
}
```
- 在 `res/xml/accessibility_service_config.xml` 里开启 `canRequestFilterKeyEvents` 和 `accessibilityEventTypes`。
- **注意**：无障碍服务需要用户在系统设置里手动开启授权（和"辅助功能"授权类似）。

**模块 B：动作执行（车控）**

这里是**本项目最大的技术不确定性**，分三种情况：

**(a) 车机开放了控制接口/无障碍可达**
- 如果空调/座椅调节在车机上表现为可操作 UI，可用无障碍服务直接 **模拟点击**：先找到控件（如温度 + 按钮），执行 click。
- 或者用 **ADB + `input` 命令**（需要能开 ADB / 车机开放 USB 调试）：`adb shell input keyevent` 等。适合开发调试，量产不现实。

**(b) 车机有第三方 App 可调车控**
- 有些品牌车机会有第三方 App 能调用空调等（通过厂商开放的平台/协议）。如果有，你的 App 就变成"按键→调用第三方App接口"的转发器。
- **这一步必须实测你的车机**，网上资料有限，需要你在车机上探索。

**(c) 车机完全封闭（车控不可被第三方操作）**
- 这时**车控类功能做不了**，App 只能做"系统级"操作（音量、切歌、导航、打开某App等）。
- 这也是为什么我强烈建议：**先做能100%成功的系统功能（媒体/音量），车控作为二期探索**。

> ⚠️ **给功能目标泼一盆冷水（重要）**：
> 「空调/座椅车控」是**最难、最不确定**的一块。因为它依赖车机是否开放对空调/座椅的控制接口。多数品牌的车控（空调、座椅、门窗）走的是厂商私有 CAN/域控协议，第三方很难染指。**我强烈建议把"空调/座椅车控"定位为探索性二期目标，把"媒体/音量/导航/一键宏"作为一期必达目标。** 这样项目能先跑通、先有成就感，再挑战难的。

## 5. 分阶段落地路线（边学边做）

### Phase 0：可行性验证（1~2 天，零硬件）
1. 车机上确认能装 APK；装一个"无障碍事件查看器/按键监视器"App，确认旋钮/按键以什么事件到达。
2. 确认车机能否开 ADB（接电脑调试）。能开 → 二期车控的想象空间大很多。
3. 决定蓝牙路径（建议 HID）。

### Phase 1：最小可跑通（1~2 周，硬件入门）
1. 买 ESP32-C3 开发板 + EC11 编码器 + 几个按键 + 面包板。
2. 用 Arduino 写个最小固件：旋钮→左右方向键，按键→键盘字母/功能键。上电连车机蓝牙。
3. 车机上装一个极简 App，用无障碍服务收到按键后 **Toast/弹窗打印**。确认链路通。
   - **目标：转动旋钮，车机上出现日志。** 这一步成功 = 整个架构成立。

### Phase 2：系统级功能落地（1~2 周）
1. App 实现：音量 +/-、播放/暂停、上一首/下一首、静音、打开导航、打开某个App等。
2. 给旋钮分配"长按/短按/旋转"多态（编码器支持按下、旋转，可组合出很多动作）。
3. 打磨：省电（自动休眠）、防误触、指示灯。

### Phase 3（可选/探索）：车控
1. 尝试 ADB 探索车机系统是否开放空调/座椅控制接口。
2. 若开放 → 实现；若不开放 → 接受现实，专注系统级+宏功能。

### Phase 4：产品化
- 3D 打印外壳、锂电池供电、Type-C 充电、外观打磨、按键布局设计。

| 部分 | 工具/库 |

| 固件 | Arduino IDE + **ESP32-BLE-Keyboard** 库（把 ESP32 变成蓝牙键盘） |

**ESP32-BLE-Keyboard 库示例片段**：
```cpp
#include <BleKeyboard.h>
BleKeyboard bleKeyboard("Knob 控制面板", "Knob", 100);

void setup() {
  bleKeyboard.begin();
}
void loop() {
  if (bleKeyboard.isConnected()) {
    if (digitalRead(BTN_VOL_UP) == LOW) {
      bleKeyboard.write(KEY_MEDIA_VOLUME_UP);
    }
    // 编码器旋转 → 左右方向键
  }
}
```

## 8. 风险与注意事项

1. **车控是最不确定的**（见第4节）：别把它当第一目标。
2. **无障碍服务权限**：每次车机重启/系统更新后可能需要重新授权；有的车机系统会限制无障碍服务。需实测。
3. **蓝牙被车机占用**：车机本身蓝牙可能用于打电话/钥匙/其他设备，HID 外设接入一般没问题，但要多设备共存时测试。
4. **安全**：避免把"一键动作"设成影响驾驶安全的操作（如切驾驶模式时注意盲操作）。
5. **保修**：改装车机软件/装 App 一般不影响整车保修，但**刷机/改系统会有风险**，建议只装第三方 App，不动系统分区。
6. **法律/合规**：仅自用学习没问题；若要量产销售，涉及蓝牙认证（BQB）、无线电型号核准（SRRC）等，成本高，非本方案范围。

## 10. 结语

这个项目的**核心思路是先跑通链路、再堆功能**。硬件端用 ESP32 + BLE HID 把复杂度降到最低，车机端用"无障碍服务读按键 + App 执行动作"把逻辑解耦。

**记住：硬件只是"手"，App 才是"大脑"。** 把"手"做对（稳定上报事件），把"大脑"做活（可配置、可扩展、可后期加车控），就是一个可玩性很高、能一直迭代的作品。
