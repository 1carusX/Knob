## 1. 现象与已知事实

| 搜索方 → 目标 | 结果 | 说明 |
|---|---|---|
| 车机 → knob | ❌ 搜不到 | 问题本身 |
| 车机 → 手机 | ✅ 搜得到 | 车机 BT 发现流程工作正常 |
| 手机 → knob | ✅ 搜得到 | knob 广播正常，固件侧没问题 |

关键事实（来自代码）：

- **ESP32-S3 只有 BLE，无经典蓝牙（BR/EDR）**。硬件层面决定 knob 永远不可能响应"经典蓝牙 Inquiry"。
- knob 广播：`ble.cpp` 主 AD 只带自定义 service UUID，**设备名放在 scan response**（`ble_init()`，`firmware/src/ble.cpp:239-244`）。
- 现有首次配对流程**依赖车机系统蓝牙设置界面**：
  - 壳只在"已配对设备"里找 knob：`BleManager.init()` 用 `adapter.bondedDevices.firstOrNull { name 前缀 "Knob-" }`（`app/.../ble/BleManager.kt:148`），搜不到就提示"先去蓝牙设置配对"（:150）。
  - 固件两个特征值都带 `*_ENC`（按键 `NOTIFY|READ_ENC`、显示 `WRITE|WRITE_ENC`，`ble.cpp:230-234`），不加密连不上 → bond 是硬前提。
  - 发按键以 `s_authenticated`（配对+加密完成）为门：`ble_is_paired()`（`ble.cpp:271-273`）、`ble_send_key*`（:286-304）。

## 2. 关键历史证据：车机协议栈"连过"knob、也"配对弹过框"

`BleManager.kt` 注释里的两段实测（都在自定义 GATT 时代前后）：

1. `app/.../ble/BleManager.kt:102-107`：
   > "实测这台车机的蓝牙栈重连 knob 时压根不发 `ACTION_ACL_CONNECTED` 广播（**系统蓝牙设置界面显示已连接**，但广播接收器完全没收到）……这台车机的蓝牙栈很多地方不按标准 AOSP 行为来。"

   → knob 与这台车机存在过 bond，断线后靠 bond 记录自动连上，**不需要重新扫描**。

2. `BleManager.kt:154-159`（autoConnect=true 时的现象）：
   > "会触发一次独立于系统 HID 连接的全新配对（**弹出跟系统配对时不一样的 6 位数**）"

   → **App 主动 `connectGatt` 触发的 SMP 配对，车机是弹系统配对框的**（6 位数 = 数字比对，与固件 `setSecurityIOCap(DISPLAY_YESNO)` 一致）。

**推论**：车机的过滤不在协议栈/服务端，而在"系统设置界面的发现与枚举"这一层。App 发起连接这条路车机是认的——这为下面的规避方案提供了直接依据。

## 3. 病根分析（按可能性排序）

1. **（最可能）车机设置界面的"搜索设备"基本以经典蓝牙 Inquiry 为主**，或它的 LE 结果列表只列它认识的类型（手机/媒体/键盘）。
   - 车机能搜到手机 = 手机开配对时以经典蓝牙 discoverable 出现 → 落入车机搜索范围；
   - knob 是 BLE-only（S3 无 BR/EDR），从未进入经典 Inquiry；
   - 于是"纯 BLE 自定义外设"在设置界面里**永远不出现，首次 bond 无从发起**。
   - 这也解释了第 2 节：bond 一旦存在（无论当初怎么建立的），重连不需要发现流程，所以"系统蓝牙设置界面显示已连接"。

2. **knob 正被其它 central 连接**（测试现场最容易踩）：BLE 外设被连接时停止广播（`onDisconnect` 里才 `startAdvertising`，`ble.cpp:163-168`），此时任何设备都搜不到它。**测车机前必须确认 knob 没连开发手机。**

3. 广告被"只看主 AD 不看 scan response"的老旧枚举漏掉（低概率，普通手机可见，但把名字并入主 AD 是零成本增强，见 W1b）。

4. 极端兜底解释：车机 BT 服务端连 App 发起的 BLE 扫描/连接都封（**与第 2 节证据冲突，可能性极低**）。若真如此只能走 W3。

## 4. 先验证（把病根钉死，再做决定）

- **V1｜壳内加"扫描 BLE"调试按钮**：`BluetoothLeScanner.startScan`（按 `Knob-` 前缀过滤），把 name/MAC/RSSI 打日志。
  - 车机上 App 扫得到 knob → 车机无线电/协议栈 OK，过滤只在设置 UI → 直接执行 W1a/W1b。
  - App 也扫不到 → 问题在协议栈/策略层，改走 V2/V3 进一步定位，规避方案要降级。
- **V2｜对照实验**：拿成品 BLE-only 外设（蓝牙键盘/鼠标）开配对，看车机设置界面列不列出——列出=车机会枚举部分 BLE 类型；不列出=基本确认设置 UI 不做通用 LE 发现。
- **V3｜nRF Connect（手机端）模拟**：用外设模式广播成 `Knob-XXXX` + 自定义 service，看车机搜不搜得到，把固件因素彻底排除。
- **V4｜测试前检查**：确认 knob 未被任何手机占用（连接中不广播）。
- **V5｜翻车机设置**：部分 ROM 有"配件/其他设备/键盘"二级类目或高级选项，BLE 外设可能藏在里面而不是主列表。

## 5. 规避方案（按推荐序）

### W1a：App 发起 createBond，绕过设置界面的"发现"（推荐，固件基本不动）

思路：Android 允许 App 自己扫描 + 对**未配对**外设发起连接/配对，不经过"蓝牙设置 → 搜索 → 点击"这条被卡死的路径。配对成功后，壳原有 `bondedDevices` + 加密连接流程原样可用。

流程：App 前台扫描（`Knob-` 前缀）→ 命中 → `device.createBond()` → 车机弹系统配对框（数字比对）→ 之后照旧。

改动点：
| 位置 | 改动 |
|---|---|
| `app/.../AndroidManifest.xml`（:8-10 附近） | +`android.permission.BLUETOOTH_SCAN`（`neverForLocation`，API 31+）；API<31 兜底 `ACCESS_FINE_LOCATION`（`minSdk 26` 需兼容） |
| `KnobActivity.kt`（`requestBluetoothPermissionAndConnect` :326-343） | 权限申请扩展成"扫描并连接"；扫描结果/配对状态打日志 |
| `BleManager.kt` | `init()` 找不到 bonded 设备时先 `startScan`（前台）；命中 `Knob-*` → `stopScan` → 首次 `createBond()` / 已有 bond 直接 `connectGatt`；把 MAC 持久化（SharedPreferences），后台重连轮询（`pollRunnable` :108-113）改成**对已知 MAC 直连**，避免后台扫描被 Android 限流 |

风险：车机 ROM 若吞掉系统配对框则此路不通（但第 2 节证据表明这台车机会弹）→ 退 W1b。

### W1b：去加密直连 + 固件 MAC 白名单（兜底，改动含固件）

适用：W1a 的配对框不弹、或想彻底摆脱系统配对依赖。代价：通道无加密，需用 MAC 白名单补偿访问控制。

固件（`firmware/src/ble.cpp`）：
- 两个特征值去掉 `*_ENC`：按键 `NOTIFY`、显示 `WRITE`（:230-234）；安全参数可保留（无 ENC 属性时不会强制起 SMP）。
- `ble_is_paired()` 的门从 `s_authenticated` 降为"已连接"（:271-273），`ble.h` 注释同步改。
- `ServerCallbacks::onConnect` 加 MAC 校验：非授权 central 直接 `disconnect`（:149-161）；配一个"授权模式"：用户长按 knob 物理键 3 秒进入，把下一个连入的 MAC 写入 NVS，之后只认它。
- 广播名字并入主 AD（不只 scan response，:239-244），提升兼容性。

壳（`BleManager.kt`）：
- `init()` 不再依赖 `bondedDevices`：`startScan` 按名找 → `connectGatt(TRANSPORT_LE)`（不配对）；MAC 持久化供后台轮询直连。
- 首连 UI：提示用户按 knob 键进授权模式。
- 其余（MTU 185、订阅 NOTIFY、断线即重连、通用键值对编码）全部沿用。

安全权衡（需明确接受）：无加密 + MAC 白名单只能挡"随手连上"，挡不了有意的 MAC 伪造。DIY 场景（无线电范围小、车在私人处）通常可接受；若在意，后续可加 OOB 随机 PIN 交换。按键数据本身只含 Tab/Enter+温度档位，无敏感信息，主要风险是他人可远程开关空调/座椅——白名单已把门槛抬到"先伪造 MAC"。

### W2：双模硬件（仅当 W1 全部被车机拒绝）

ESP32-S3 无经典蓝牙。若实测连 W1 的 App 直连也被车机协议栈封（与第 2 节证据矛盾，基本不会发生），再考虑换 ESP32（双模，经典可被发现）+ SPP/经典 HID 协议改造——工程量大，暂不推荐。

### W3：手机中继（终极兜底）

车机搜得到手机≠第三方 App 能拿 HFP/A2DP 的数据通道。需手机 BLE 连 knob + 车机 App 走热点/云与手机通信。仅当车机 BT 对第三方 App 彻底封闭时考虑。

## 6. 建议执行顺序

```
V1（壳内扫描诊断，10 分钟） ── 确认病根
        │ 扫得到（预期）
        ▼
W1a（App 扫描 + createBond，固件不动）
        │ 配对框不弹？
        ▼
W1b（去加密 + MAC 白名单 + 名字入主 AD）
```

所有步骤都不依赖车机厂商签名，可先在普通 Android 手机上联调（`plugin-simulate.dex` 链路），最后一次上车。

## 7. 结论一句话

车机搜不到 knob，最可能是**车机设置界面的发现流程不枚举纯 BLE 自定义外设**（knob 是 BLE-only），而不是广播坏了或类型拉黑——车机协议栈此前已被证明能对 knob 完成 App 触发的配对连接。**规避方向：让壳 App 自己扫描并发起连接/配对，绕开设置界面**；需要动固件的只有去加密兜底档（W1b）。
