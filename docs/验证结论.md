# 实车验证结论（持续更新）

> 来源：车机端 App 内日志（无 adb 环境下的唯一观测记录）。
> 测试 App：CarProbe（Knob 壳的前身）。

## 结论速览

| # | 结论 | 证据 |
|---|------|------|
| 1 | `BYDAUTO_AC_COMMON` / `BYDAUTO_SETTING_COMMON` 是 **dangerous 级**（protectionLevel=1），运行时申请后**可被授予** ✅ | log_20260827_121155（保护级别探测）、log_20260827_140138（授权成功） |
| 2 | `BYDAUTO_AC_GET/SET`、`BYDAUTO_SETTING_GET/SET` 是 **signature 级**（protectionLevel=2），普通签名 App **不被授予** ❌ | log_20260827_121155、log_20260827_140138（检查权限） |
| 3 | 车控写操作被系统服务端拒绝：`SecurityException - [setIntArray] permission deny!`（setAcTemperature / setAcTemperatureControlMode） | log_20260827_140138 |
| 4 | `hasFeature` 查询被拒：`[getInt] permission deny!` → 设备初始化时无法探测 feature | log_20260827_140138 / 143325 |
| 5 | 座椅通风调用抛 `InvocationTargetException: null`（`setSeatVentilatingState`，BydHal.kt:183）→ 参数或权限未达 HAL | log_20260827_140138 / 143325 |
| 6 | 读空调温度返回 `-2147482645`（BYDAUTO_COMMAND_RESULT 参数无效/不可读） | log_20260827_140138 / 143325 |
| 7 | 未申请权限时初始化设备直接 `SecurityException - Neither user 10094 nor current process has ...` → 必须走运行时授权 | log_20260826_212555 |

## 关键推论

- **第三方普通签名 App 无法直接 BYDAUTO 车控**：GET/SET 权限是 signature 级（已实测）。能直接控车的应用都持有车机厂商签发的签名。
- **不存在额外的包名白名单机制**：权限门槛就是签名本身——拿到车机厂商签发的签名即可获得对应权限，不需要额外的包名注册/白名单审批。
- 由此确定架构方向：**壳用车机厂商签名签一次（进程 UID 继承权限）→ 业务逻辑放 plugin.dex 热加载**。签名已通过官方开发者认证流程申请到位。
- ❌ **无障碍方案已弃用**：最初计划用无障碍服务捕获蓝牙 HID 按键上报，实测目标车机的定制系统没有暴露无障碍服务的开关入口，无法启用，这条输入路径确认走不通。现已替换为完全自定义的双向 BLE GATT 通道（详见 `docs/项目历程与架构.md`），无障碍服务在本项目中不再使用。
