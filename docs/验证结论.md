# 实车验证结论（持续更新）

> 来源：车机端 App 内日志（无 adb 环境下的唯一观测记录）。
> 测试 App：CarProbe（Knob 壳的前身）。

## 结论速览

| # | 结论 | 证据 |
|---|------|------|
| 1 | `BYDAUTO_AC_COMMON` / `BYDAUTO_SETTING_COMMON` 是 **dangerous 级**（protectionLevel=1），运行时申请后**可被授予** ✅ | 保护级别探测；运行时申请后授权成功 |
| 2 | `BYDAUTO_AC_GET/SET`、`BYDAUTO_SETTING_GET/SET` 是 **signature 级**（protectionLevel=2），普通签名 App **不被授予** ❌ | 保护级别探测；检查权限显示未授予 |
| 3 | 车控写操作被系统服务端拒绝：`SecurityException - [setIntArray] permission deny!`（setAcTemperature / setAcTemperatureControlMode） | 调用空调写接口时的异常 |
| 4 | `hasFeature` 查询被拒：`[getInt] permission deny!` → 设备初始化时无法探测 feature | 设备初始化时的异常 |
| 5 | 座椅通风调用抛 `InvocationTargetException: null`（`setSeatVentilatingState`，BydHal.kt:183）→ 参数或权限未达 HAL | 调用座椅通风时的异常 |
| 6 | 读空调温度返回 `-2147482645`（BYDAUTO_COMMAND_RESULT 参数无效/不可读） | 读空调温度的返回值 |
| 7 | 未申请权限时初始化设备直接 `SecurityException - Neither user 10094 nor current process has ...` → 必须走运行时授权 | 未申请权限就初始化设备时的异常 |
| 12 | 车机上定义的 BYDAUTO 权限，探测能列出来的只有 20 个 `*_COMMON`，全部 dangerous、定义包=android；GET/SET 一个都列不出来（`AC_GET` 已授予也不在任何可见包的声明里），所以 GET/SET 的名字没法在车上查 | 厂商签名壳上运行 `probeBydPermissions`：可见包 204 个，共 20 个 |
| 13 | 车速（Speed）、车身（Bodywork）设备两层都要：先缺 `*_COMMON` 报 `Neither user … has BYDAUTO_BODYWORK_COMMON`；运行时授权 COMMON 后改报 `[getInt] permission deny!`，即缺 signature 级 `*_GET`（与 #4、#7 当年的空调同一模式）。厂商签名壳只声明了 AC/SETTING 的 GET/SET，这两个设备初始化失败 | 厂商签名壳授权 SPEED/BODYWORK_COMMON 前后两次自检 |
| 14 | 壳已按 `BYDAUTO_<设备>_GET/SET` 命名补全各设备的 GET/SET 声明（含 `SPEED_GET`、`BODYWORK_GET`），待重签后实车确认车速/车身能否初始化、这些名字是否真实存在 | 待验证 |

## 固件 OTA（手机实测，车机待验）

> 测试机：小米 24091RPADC，Android 16（API 36），`generic` 壳 + 模拟版插件包，旋钮为自制 PCB。车机（Android 12）上还没验证，下面的结论不能直接当成车机结论。

| # | 结论 | 证据 |
|---|------|------|
| 8 | 插件打成 zip、壳原样存成 `plugin.dex`，`DexClassLoader` 能正常加载（ART 按文件头认 zip）；插件能用 `ZipFile` 按路径读出包里的固件 | 导入后 `插件导入并加载成功`、`📦 插件包带固件 <版本>（pcb）` |
| 9 | 自动 OTA 连续成功两次（`2c3994a` → `0.1.0+aac720b` → `0.1.1+3da9939`）：校验通过、重启、自动重连，读到的版本跟包里一致后停止升级 | `✅ 旋钮校验通过` → 重连 → `已是插件包里的版本` |
| 10 | 1.1 MB 固件传输约 72 秒（约 15 KiB/s，每包 507 字节约 33 毫秒，带应答逐包写）；从开始到重连读到新版本共约 80 秒 | 日志时间戳 |
| 11 | 刷了新固件后手机仍用缓存的旧 GATT 服务列表，看不到新特征值，反射调 `BluetoothGatt.refresh()` 后重新发现即可 | 第一次发现服务缺 `468889d4`，清缓存后再发现就有了 |

## 关键推论

- **第三方普通签名 App 无法直接 BYDAUTO 车控**：GET/SET 权限是 signature 级（已实测）。能直接控车的应用都持有车机厂商签发的签名。
- **不存在额外的包名白名单机制**：权限门槛就是签名本身——拿到车机厂商签发的签名即可获得对应权限，不需要额外的包名注册/白名单审批。
- 由此确定架构方向：**壳用车机厂商签名签一次（进程 UID 继承权限）→ 业务逻辑放 plugin.dex 热加载**。签名已通过官方开发者认证流程申请到位。
- ❌ **无障碍方案已弃用**：最初计划用无障碍服务捕获蓝牙 HID 按键上报，实测目标车机的定制系统没有暴露无障碍服务的开关入口，无法启用，这条输入路径确认走不通。现已替换为完全自定义的双向 BLE GATT 通道（详见 `docs/项目历程与架构.md`），无障碍服务在本项目中不再使用。
- ✅ **车机蓝牙设置界面按设备类型过滤扫描结果，只列手机 / HID 类设备**：纯自定义 GATT 的旋钮（ESP32-S3 只有 BLE）在设置界面里搜不到；固件广播加上 Appearance=键盘 + 一个标准 HID 服务（0x1812）后能搜到。这个 HID 服务只用来通过过滤，真正的按键/显示仍走自定义 GATT（`105d868`，`firmware/src/ble.cpp`）。分析过程见 `docs/车机蓝牙发现问题-诊断与规避方案.md`。
